# Regulation-to-Control Matrix (SCOF)

Last updated: 2026-11-19. Verification was done by checking the cited primary sources and, where noted, by reviewing the relevant official text and Gazette instruments.

## 1. At a glance

SCOF checks Terraform plans against eight technical controls. Each control is tied to its sources in this document; where no source requires the exact check, the control is labelled an interpretation. Applicability to a given organisation is always a separate question (see section 8).

### 1.1 Which controls apply in which context

| Control | india-finance | eu | india-healthcare | india (sector-neutral) |
|---|---|---|---|---|
| REGION-RESTRICTION | Yes (India regions) | Yes (EU regions) | No | No |
| DATA-ENCRYPTION | Yes | Yes | Yes | Yes |
| KEY-OWNERSHIP | Yes | Yes | Yes | Yes |
| KEY-ROTATION | Yes | Yes | Yes | Yes |
| IAM-NO-WILDCARD-ADMIN | Yes | Yes | Yes | Yes |
| LOG-RETENTION | Yes | No | Yes | Yes |

| BACKUP-RESILIENCE | Yes | Yes | Yes | Yes |

### 1.2 What each control checks and where it comes from

| Control | What SCOF checks in the plan | Main basis | How it relates to the law |
|---|---|---|---|
| REGION-RESTRICTION | The provider region is in the context's allow-list | india-finance: S1; eu: S6 | Stricter than the law: S1's foreign-leg exception and GDPR's transfer routes are not modelled |
| DATA-ENCRYPTION | S3 buckets use KMS encryption and have a configuration; RDS, standalone EBS volumes and all EC2 block devices are encrypted | S2 Rule 6(1)(a), S5 Art 32(1)(a), S31–S33 | Stricter: the sources name encryption but not AWS KMS |
| KEY-OWNERSHIP | Referenced KMS keys are customer-managed | None (interpretation) | SCOF engineering choice |
| KEY-ROTATION | KMS key rotation is enabled | None (interpretation) | SCOF engineering choice |
| IAM-NO-WILDCARD-ADMIN | No policy allows every action on every resource | S2 Rule 6(1)(b); S31–S33 | Narrow proxy for least privilege |
| LOG-RETENTION | CloudWatch log groups keep logs for at least 365 days | S2 Rule 6(1)(c) and (e); S42 (180 days in India) | Conservative baseline; the numbers 180, 365 and five years are different duties |
| ACCESS-EXPOSURE | No explicitly public S3 bucket or RDS instance | S2 Rule 6(1)(b); S5 Art 32 | Narrow proxy; no source names public S3 or RDS |
| BACKUP-RESILIENCE | RDS automated backups are set to at least one day | S31–S33; S5 Art 32(1)(c); S2 Rule 6(1)(d) | One day is a SCOF baseline, not a legal number |

### 1.5 What this matrix does not claim

- It is not legal advice and does not decide whether a law applies to a given organisation.
- Only eight controls exist. Obligations a Terraform plan cannot show are listed in the not-assessable ledger (section 8), not turned into extra controls.
- A check is a technical interpretation unless a source requires that exact check.
- Only root-module Terraform configurations are supported. The encryption and key-ownership checks look each resource up in the root module, so a resource inside a Terraform module is reported as unencrypted or without a customer-managed key even when it has both.

## 2. How to read this matrix

Status labels:
- VERIFIED-PRIMARY: the relevant source text was checked against the issuing authority's official page, Gazette or official instrument.
- VERIFIED-SECONDARY: confirmed through secondary material; the relevant primary text has not yet been checked.
- INTERPRETATION: our technical reading. No verified legal text requires this exact control.
- NOT VERIFIED: do not rely on the source as an operative legal requirement. This includes sources whose text could not be checked.
- A draft that is VERIFIED-PRIMARY means only that the draft itself was checked and is authentic; it does not make the draft operative.

Each control follows one chain: source, requirement, control, Terraform attribute, Rego rule, fixture. One control has one Rego rule. Which controls apply, and with which parameters, is decided by the routing context (section 3).

Source IDs (S1–S44) are used throughout. Section 6 lists them by regime with a one-line summary; Appendix A holds the full note for each source.

## 3. Routing contexts

SCOF routes four contexts: `india-finance`, `eu`, `india-healthcare` and the sector-neutral `india`. Choosing a context does not establish that every healthcare source applies to every workload or that any technical safeguard is a legal requirement. Entity, participant, establishment, data, activity and territorial applicability must still be assessed (NA-01, NA-24 and NA-26).

DPDP and GDPR are sector-neutral, subject to their respective scope and commencement rules. RBI sources are entity-/activity-specific. ABDM, MHCA and CEA/State-UT instruments have their own participant, establishment, authority and territorial conditions. No healthcare source recorded in S19–S30 establishes a universal India-only cloud-hosting rule.

| Layer | Applies when | Controls (parameters) |
|-------|--------------|-----------------------|
| Base | always | DATA-ENCRYPTION, KEY-OWNERSHIP, KEY-ROTATION, IAM-NO-WILDCARD-ADMIN, ACCESS-EXPOSURE, BACKUP-RESILIENCE |
| Jurisdiction | jurisdiction = EU | REGION-RESTRICTION (eu list) |
| Jurisdiction | jurisdiction = India | LOG-RETENTION |
| Sector overlay | jurisdiction = India and sector = finance | REGION-RESTRICTION (india-finance list) |

Contexts and their control composition:

- `india-finance`: base + LOG-RETENTION + REGION-RESTRICTION (India list), subject to the existing S1 payment-system data applicability limits.
- `eu`: base + REGION-RESTRICTION (EU list). LOG-RETENTION is not enabled.
- `india-healthcare`: six base controls + India LOG-RETENTION. No REGION-RESTRICTION is added: the supplied sources do not establish universal India-only hosting for healthcare data. This context mapping is a conservative SCOF baseline, not a finding that every healthcare workload or provider is subject to every Indian log-retention obligation.
- `india`: sector-neutral India context (a deployment in India with no sector); base + LOG-RETENTION, no region rule. Its control set is identical to `india-healthcare`. Routing it does not mean that DPDP imposes a sector-neutral deployment profile; the Indian controls remain readiness baselines (DPDP Rule 6 is not yet in force, about 13 May 2027).

The context compositions are exact:

- `india-finance`: six base controls + LOG-RETENTION + REGION-RESTRICTION (India list).
- `eu`: six base controls + REGION-RESTRICTION (EU list); no LOG-RETENTION.
- `india-healthcare`: six base controls + India LOG-RETENTION (India jurisdiction layer); no REGION-RESTRICTION.
- `india`: six base controls + LOG-RETENTION (India jurisdiction layer); no region rule; sector-neutral.

The six base controls are DATA-ENCRYPTION, KEY-OWNERSHIP, KEY-ROTATION, IAM-NO-WILDCARD-ADMIN, ACCESS-EXPOSURE and BACKUP-RESILIENCE. The finance-specific REGION-RESTRICTION overlay is not inherited by `india-healthcare`. The existing eight control definitions, thresholds and technical meanings are unchanged; this routing composition selects existing controls and parameters only.

**LOG-RETENTION applicability boundary:** enabling LOG-RETENTION in an India jurisdiction context is a conservative SCOF baseline. It is not a legal applicability determination and does not prove that every healthcare workload is subject to every Indian logging/retention obligation. Applicability must be established per entity, activity, service-provider class, data and instrument (NA-24/NA-26). Keep these requirements distinct:

- CERT-In Directions para (iv): rolling 180-day ICT logs securely maintained within Indian jurisdiction for entities within the Direction's covered classes and scope.
- RBI S33 para 27(e): at least five years for specified audit-log records of covered non-bank PSOs; it is not a universal healthcare or general India requirement.
- DPDP Rules 2025: the specified one-year retention duties in Rule 6(1)(c)/(e) and Rule 8(3) are future-effective on the schedule recorded in S2/S21/S22 (13 May 2027) and remain subject to their exact purpose, entity and statutory applicability.
- Existing SCOF technical proxy: the current 365-day CloudWatch log-group check is a narrow Terraform-plan signal. It does not prove all ICT systems are logged, India-jurisdiction storage, required event coverage, log integrity, access/review, the five-year PSO category-specific requirement, future DPDP compliance, or complete regulatory compliance.

No healthcare-specific technical control is defined; the existing eight controls apply in `india-healthcare`.

## 4. Controls

Control IDs are context-neutral and name the technical check. One control has one Rego rule. Which controls apply, and with which parameters, is decided by the routing context (see Routing contexts). The legal basis can differ per context and is recorded under each control.

### REGION-RESTRICTION
- Check: the AWS provider region must be in the allowed list supplied by the routing context. One Rego rule; the router passes the list.
- Terraform attribute: configuration.provider_config.aws.expressions.region.constant_value (literal region).
- Rego rule: policies/region.rego (implemented).
- Allowed lists (parameters; store as data, do not hardcode in Rego):
  - india-finance: ap-south-1, ap-south-2. Based on [AWS's documented region geographies.](https://docs.aws.amazon.com/global-infrastructure/latest/regions/aws-availability-zones.html#zones-asia-pacific)
  - eu: eu-central-1, eu-west-1, eu-west-3, eu-north-1, eu-south-1, eu-south-2. Excludes eu-west-2 (United Kingdom) and eu-central-2 (Switzerland), based on [AWS's documented region geographies.](https://docs.aws.amazon.com/global-infrastructure/latest/regions/aws-availability-zones.html#zones-europe)
- Legal basis per context:
  - india-finance: S1 (RBI). Legal content (as verified): payment system data to be stored in systems located only in India (scope: RBI-authorised payment system providers; payment data). SCOF interpretation: AWS resources of an India finance workload that holds payment data must be deployed in India regions. Caveats: covers payment data only, not all financial data. RBI also allows the foreign leg of a cross-border transaction to be stored abroad; this rule does not model that exception, so it is stricter than the circular. Backups, replication and global services are not modelled. DPDP is not the source of this control (S4: no blanket India-only storage requirement).
  - eu: S6 (GDPR Art 44), S5 context. Legal content (as verified): transfers to third countries are allowed only if Chapter V conditions are met. SCOF interpretation (conservative): for an EU deployment context, deploy only in EU regions so that no third-country transfer arises. Caveats: GDPR does not require EU-only storage; adequacy decisions and safeguards (Arts 45-46) are not modelled.
  - india without a sector (context `india`, sector-neutral, as `eu` is for the EU): no region restriction; no verified source provides one (S4). The base DPDP-derived controls and LOG-RETENTION apply as readiness baselines.
- Fixtures: india-finance PASS s3_kms_cmk_india, rds_encrypted_cmk_india, ec2_encrypted_cmk_india, kms_rotation_enabled_india, iam_least_privilege_india; FAIL s3_wrong_region, rds_wrong_region. eu PASS s3_kms_cmk_eu. 
- Cross-context check: India fixtures evaluated under the eu context fail REGION-RESTRICTION as expected.

### DATA-ENCRYPTION
- Basis (all contexts): S2 Rule 6 and S5 Art 32.
- Legal content (as verified): reasonable or appropriate security measures, with encryption named as one example. Neither text names KMS or any AWS service. DPDP Rule 6 commences 18 months after notification (about 13 May 2027, per Rule 1), so that basis is not yet in force; GDPR Art 32 is in force.
- SCOF interpretation: persistent storage must be encrypted with AWS KMS. SSE-S3 (AES256) is still encryption, so the fixture s3_no_kms_encryption violates our stricter KMS control, not necessarily the law.
- Check: every S3 server-side encryption configuration uses sse_algorithm aws:kms, and every aws_s3_bucket has such a configuration; every aws_db_instance sets storage_encrypted to true; every standalone aws_ebs_volume sets encrypted to true; every EC2 block device (root and extra EBS) sets encrypted to true; an EC2 instance with no explicit root_block_device is denied.
- Terraform attributes: aws_s3_bucket_server_side_encryption_configuration (rule.apply_server_side_encryption_by_default.sse_algorithm); aws_db_instance.storage_encrypted; aws_ebs_volume.encrypted; aws_instance.root_block_device[].encrypted and aws_instance.ebs_block_device[].encrypted; the presence of an encryption configuration for each aws_s3_bucket.
- Rego rule: policies/encryption.rego (implemented).
- Fixtures: FAIL s3_no_kms_encryption, rds_unencrypted, ec2_unencrypted_ebs. PASS the compliant set.

### KEY-OWNERSHIP
- Basis: none verified. INTERPRETATION.
- Rationale: control over the key lifecycle supports "appropriate technical measures"; no verified text requires customer-managed keys.
- Check: referenced KMS keys must be customer-managed (an aws_kms_key resource or a CMK ARN), not an AWS-managed alias (alias/aws/*).
- Terraform attributes: kms_master_key_id (S3), kms_key_id (RDS, EBS). References to keys created in the same plan are unknown at plan time, so read configuration.root_module.resources[].expressions.<attr>.references.
- Rego rule: policies/key_ownership.rego (implemented).
- Fixtures: FAIL s3_aws_managed_key.

### KEY-ROTATION
- Basis: none verified. INTERPRETATION (security best practice).
- Check: aws_kms_key.enable_key_rotation is true.
- Rego rule: policies/key_rotation.rego (implemented).
- Fixtures: FAIL kms_rotation_disabled. All compliant fixtures with keys set rotation to true.

### IAM-NO-WILDCARD-ADMIN
- Basis: S2 Rule 6 (access control is among the minimum safeguards), VERIFIED-PRIMARY. The wildcard-admin rule is our INTERPRETATION of "access control"; Rule 6 does not mention IAM or wildcards. Rule 6 commences about 13 May 2027 (Rule 1), so the DPDP basis is not yet in force.
- Check: no IAM policy statement may Allow Action "*" on Resource "*". A policy document that is unknown at plan time (for example one that refers to a resource created in the same plan) is denied, because it cannot be verified.
- Terraform attribute: aws_iam_policy.policy (JSON string, parse with json.unmarshal in Rego).
- Rego rule: policies/iam.rego (implemented).
- Fixtures: FAIL iam_wildcard_admin. PASS iam_least_privilege_india.

### LOG-RETENTION
- Status: INTERPRETATION — The security objective is supported, but the one-year requirement is applied to all CloudWatch log groups for implementation purposes.
- Basis: S2 Rule 6(1)(c) and 6(1)(e), VERIFIED-PRIMARY. DPDP only. No verified EU source requires one-year log retention, so the control is not enabled in the eu context.
- Legal content (as verified, paraphrased): Rule 6(1)(c) requires visibility on access to personal data through appropriate logs, monitoring and review. Rule 6(1)(e) requires such logs and personal data to be retained for one year, unless another law in force requires otherwise. Rule 8(3) separately describes a minimum of one year for its own purposes. Rule 6 commences about 13 May 2027, so this basis is not yet in force.
- SCOF interpretation : one year is read as a floor, not an exact period. The check is applied to every CloudWatch log group in the plan, because the plan does not show which log groups hold access logs for personal data.
- Check: aws_cloudwatch_log_group.retention_in_days must be at least 365. An absent value or 0 (never expires) passes. A value that is unknown at plan time is denied (fail closed), because it cannot be verified.
- Terraform attribute: aws_cloudwatch_log_group.retention_in_days.
- Rego rule: policies/log_retention.rego (implemented).
- Applies to contexts: india, india-finance, and india-healthcare. Not enabled in eu.
- Limits: broader than the rule (all log groups, not only access logs for personal data). Not modelled: the other-law exception, S3 access logs, CloudTrail, logs kept outside CloudWatch, retention of the personal data itself, and any conflict between never-expire logs and erasure duties.
- Fixtures: FAIL log_group_short_retention_india (30 days, india-finance). PASS log_group_retention_365_india (365 days, india-finance) and log_group_short_retention_eu (30 days, eu: the control is not enabled there). The plan of log_group_short_retention_india evaluated under eu reports REGION-RESTRICTION only, with no LOG-RETENTION finding.

### ACCESS-EXPOSURE
- Status: INTERPRETATION — The security objective is supported, but “no public S3/RDS” is an implementation interpretation.
- Basis: S2 Rule 6(1)(b), VERIFIED-PRIMARY, not yet in force. GDPR Art 32(1) (S5), in force. GDPR Art 5(1)(f) (S7) is VERIFIED-PRIMARY and is used only as supporting basis; it does not specifically require blocking public S3 or RDS exposure, so the check remains a SCOF technical interpretation.
- Legal content (as verified, paraphrased): Rule 6(1)(b) requires appropriate measures to control access to the computer resources used by the Data Fiduciary or its Data Processor. Art 32(1) requires technical and organisational measures appropriate to the risk, including confidentiality (see S5). Neither text mentions public access, S3 or RDS.
- SCOF interpretation : explicit public exposure of a data store is a failure to control access.
- Check: no aws_s3_bucket_public_access_block has any of block_public_acls, block_public_policy, ignore_public_acls or restrict_public_buckets set to false, and no aws_db_instance has publicly_accessible set to true.
- Terraform attributes: aws_s3_bucket_public_access_block (the four flags); aws_db_instance.publicly_accessible.
- Rego rule: policies/access_exposure.rego (implemented).
- Applies to contexts: all (base control set).
- Limits: only explicit exposure is detected. A bucket with no public-access-block resource, public bucket policies or ACLs, security groups and account-level block settings are not modelled, so false negatives are accepted.
- Fixtures: FAIL s3_public_access_block_open_india (block_public_policy false) and rds_publicly_accessible_india (publicly_accessible true), both under india-finance. PASS s3_public_access_block_all_india. The existing compliant RDS fixtures set no publicly_accessible and plan it as false, so they pass without changes.

### BACKUP-RESILIENCE
- Status: INTERPRETATION — The resilience objective is supported, but “RDS automated backups of at least 1 day” is a SCOF technical baseline.
- Basis: for RBI regulated entities (india-finance context), the backup and restoration requirements of the 2026 entity-specific Directions (S31 paras 169–174; S32 para 8(9) and paras 129–138; S33 para 20(f); see S8 for the consolidation). S2 Rule 6(1)(d), VERIFIED-PRIMARY, not yet in force. GDPR Art 32(1)(c) (S5), in force.
- Legal content (as verified, paraphrased): Rule 6(1)(d) requires reasonable measures for continued processing if the confidentiality, integrity or availability of personal data is compromised, naming data-backups as an example. Art 32(1)(c) concerns the ability to restore availability of and access to personal data in a timely manner after an incident (see S5). The 2026 RBI Directions (S31, S32, S33) require regulated entities to back up data, periodically test restoration, and protect the integrity of and access to backups, each with its own detail for its own entity class (see the Control basis summary). None of these texts requires automated backups, RDS, or a number of days.
- SCOF interpretation : enabled RDS automated backups are a reasonable technical measure toward the backup obligations in the RBI Directions (S31–S33), Rule 6(1)(d) and Art 32(1)(c). The threshold of at least 1 day is SCOF's technical implementation baseline for ensuring that automated RDS backups are enabled, not a numeric requirement of any of those texts.
- Check: aws_db_instance.backup_retention_period must be set explicitly to at least 1. A value below 1 is denied. An omitted value is denied too: the plan reports it as unknown until apply, and the AWS provider documents a default of 0, which disables automated backups ([provider documentation, read 2026-10-05](https://github.com/hashicorp/terraform-provider-aws/blob/main/website/docs/r/db_instance.html.markdown)).
- Terraform attribute: aws_db_instance.backup_retention_period.
- Rego rule: policies/backup_resilience.rego (implemented).
- Applies to contexts: all (base control set).
- Basis of the threshold : at least 1 day is the SCOF technical baseline for ensuring that automated RDS backups are enabled. It is not a numeric requirement of the RBI Directions, DPDP Rule 6(1)(d) or GDPR Art 32(1)(c): none of them names a number of days. An explicit value is required: a value below 1 is denied, and so is an omitted value (see Check).
- Applicability of the RBI basis (S31–S38): each 2026 Direction applies only to its own regulated-entity class (see the S31–S38 rows), not to every organisation in India. The RBI basis therefore applies to the india-finance context, which assumes the deployment belongs to such an entity; SCOF does not check whether a given deployment is in scope. In the other contexts the control rests on S2 Rule 6(1)(d) and S5 Art 32(1)(c).
- Limits: RDS aws_db_instance only. Enabled automated backups do not show that backups are periodically restored and verified, that their integrity is preserved, or that access to them is restricted (the RBI backup and restore provisions); none of that is modelled. S3 versioning, EBS snapshots, Aurora clusters and cross-region copies (which could also interact with REGION-RESTRICTION) are not modelled either.
- Fixtures: FAIL rds_no_backup_india (backup_retention_period = 0) and rds_backup_not_set_india (attribute omitted, unknown at plan time), both under india-finance. PASS rds_encrypted_cmk_india, which now sets backup_retention_period = 7 explicitly. The other RDS fixtures and the terraform/rds reference configuration also set it explicitly, so that each keeps its single intended violation.

### Interpretation and applicability notes

- S31–S38 are not one universal RBI baseline. Apply the exact regulated-entity class, NBFC layer, chapter and clause. S34–S38 are limited repeal/savings checks in this research and must not be treated as complete substantive control mappings.
- S33 is specifically for authorised non-bank PSOs. Unregulated ecosystem entities are reached through mutual-agreement arrangements where specified; a vendor is not directly regulated merely because it supplies a PSO.
- S42 para (ii) incident reporting within six hours and S31 para 182 RBI reporting within six hours are separate reporting duties. Neither is proven by LOG-RETENTION or any other current Terraform control. S42 para (v) five-year customer/subscriber-information retention for specified providers is also distinct from para (iv) ICT logs.
- S43 Q35 is not treated as an amendment or definitive offshore-only exemption from S42 para (iv). The matrix adopts the conservative interpretation described in S43; this is not a judicial determination.
- DPDP Act/Rules provisions with scheduled commencement must not be described as presently operative before their effective dates. In particular, the 2027 Rule 6/Rule 8(3) requirements are future bases as of this matrix date.
- No S31–S44 provision establishes a general customer-managed-key mandate, a KMS key-rotation interval, a blanket India-only rule for all finance data, or a GDPR EU-only storage requirement.
- Legal applicability is a gate, not a Terraform property. Confirm workload data, processing purpose, entity status, regulated activity, DPDP/GDPR scope, State/UT adoption and contractual role before treating a source as applicable (NA-24 and NA-26).

The following obligations remain outside the current eight technical controls: complete audit-log coverage/review, incident detection and notification, processor contracts, independent audit, BCP/BIA governance, restore testing, RTO/RPO validation, DR-site geographic/seismic separation, vendor coordination, lawful processing, consent, notices, grievance handling, transfer mechanisms and healthcare-specific registration/records. They remain in the Not-Assessable ledger; no ninth control is introduced.
